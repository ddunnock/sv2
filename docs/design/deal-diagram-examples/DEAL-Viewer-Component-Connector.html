Connector — definition & dependency relationships

v0.1 · 2026-06-11 · Reference implementation for spec rules RG-10 (connector notation), RG-3.1 (orthogonal + rounded bends), RG-7.5 (traceability) · Companion to DEAL-Viewer-Layout-Rules-Spec.html and DEAL-Viewer-Component-ElementBox.html

The second atomic component: framework-free JS producing SVG connectors from routed points (the layout pipeline's Route stage supplies the polyline; this component draws it). Ten primary relationship kinds live in a closed registry — glyph geometry is exact and shared, lines are shortened so they never poke through hollow glyphs, and every connector carries the stable identity of its relationship declaration for go-to-definition into the owning .deal/.dealx file. Relational and action-oriented connectors are a future companion document — same registry mechanism, more entries.

1. The registry — ten primary connectors

Hover any sample: the line thickens (paint only), dwelling ~½s raises the explainer card (RG-10.12) — a plain-language reading of the relationship ("The SteeringWheel part satisfies the SteeringMechanism requirement"), what it means, and what the arrow direction tells you. Cmd/Ctrl+click reports the navigate target below — same RG-7.5 contract as element boxes. Glyph meaning lives in shape, never color: connectors render neutral in every theme and survive grayscale.

2. Zoom consistency

Pure vector, no non-scaling-stroke tricks: glyphs, line weight, and bend radii scale proportionally with diagram zoom, so a connector reads identically at every level — exactly what the canvas transform produces in the viewer (RG-5). Below the 0.3 LOD band edge labels drop, but glyphs persist (RG-6.2).

3. Routed example — orthogonal vs. curved (RG-10.6)

The same Route-stage waypoints rendered in both per-view routing styles. Orthogonal (default): rounded 6px bends per RG-3.1. Curved: a smooth cubic chain through the same obstacle-avoiding waypoints, with handle lengths clamped so the curve never deviates from the polyline by more than the 12px routing buffer — the no-cross guarantee (INV-1) holds in both styles by construction. Endpoint tangents align with the final segment, so glyphs sit identically in both:

Routing style is a per-view representation choice persisted in the .dealview tool-managed block (RG-8.2) — one setting for the whole view, never per connector, so diagrams stay stylistically coherent.

4. Approach discipline (RG-10.7)

Two rules prevent the "glitchy" look of bends crowding the arrowhead: the approach must be perpendicular to the element face (axis-aligned, never at a corner — corner clearance 8px per RG-3.3), and the line must stay straight for the glyph length + 12px run-out before its first bend, in both routing styles (curved mode pins the run-out zone straight with synthetic waypoints). The component validates every connector against these rules and emits diagnostics for violations — rendering them flagged rather than hiding them, since fixing geometry is the Route stage's job:

5. Crossings & same-source bundling

Crossings (RG-10.8): orthogonal crossings are always one horizontal × one vertical segment — perpendicular by construction (INV-6) — and the hop rule is deterministic: the horizontal segment carries the Visio-style bump (4px semicircle, bulging up), so exactly one line hops per crossing, never both. Hops closer than 10px merge into one wider hop. Collinear overlapping segments are a Route violation (≥12px edge–edge spacing, RG-2.4) and surface as diagnostics:

Bundling (RG-10.9): connectors of the same kind from the same source merge into a shared trunk while their corridors stay within 24px, splitting as a plain T-junction — no dot (the filled circle is reserved as proxy-label notation; since crossings always carry hops, an unhopped meeting unambiguously reads as a branch). When the glyph end is the shared end — composite diamonds at the owner — the bundle carries one shared glyph on the trunk; target-end glyphs render per branch. Every branch keeps its own data-ref, so traceability survives the merge:

6. Association — inline keyword label & slide (RG-10.10/10.11)

The association arrow (filled barbed head) serves multiple relationship uses: «keyword»-qualified («satisfy», «import», «type», …) or bare for action succession (then). The keyword is always horizontal (never rotated) and sets into a break in the tail — italic 11px; on horizontal segments the line gap is the label width + 12px, on vertical segments the label sits perpendicular to the line, straddling it, with a gap of the text height + 12px. Initial placement is automatic: centered on the longest hosting segment (horizontal preferred on ties), outside the run-out zones. Drag the label to slide it anywhere along the line — including vertical portions — the only user-adjustable geometry in the viewer (a representation-state adjustment, not layout editing): the normalized position persists to the .dealview tool-managed block and survives re-renders until a relayout invalidates it:

labelAt: auto (longest-horizontal-segment rule)

Unlabeled variant: bare succession (then) — same glyph, no break.

labelAt: 0.450 (persisted)

Curved routing (RG-10.6): the line can't host a clean break, so the label renders in the RG-3.7 halo style beside the path — still horizontal regardless of the tangent angle beneath it, still draggable along the route, and still persisting labelAt.

7. Ports — boundary connection points (RG-9.9)

Ports are rounded squares straddling their owner's boundary with an opaque fill (the boundary line never shows through), an optional flow-direction glyph (in ←, out →, inout ↔ along the port's axis), and a horizontal name: PortDef label outside. Ports nest — a port's own boundary hosts child ports, as the reference shows. The flow glyph rotates with the hosted edge: on a top or bottom (N/S) edge the arrows run vertically, along the connector tail — in always points from outside the boundary to inside, out from inside to outside (see the N-side tx/rx pair, right). Connectors attach to a port's outer face under the RG-10.7 approach discipline; every port carries its data-ref (RG-7.5):
