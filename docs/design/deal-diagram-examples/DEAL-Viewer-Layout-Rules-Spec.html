DEAL Viewer — Automatic Diagram Layout Rules Specification

Version 0.2 (draft) · 2026-06-11 · Produced via phased Q&A + research + skeptic evaluation · Companion to dealview.ebnf (GV-9, GV-13) · 0.2: added RG-9 SysML v2 notation rules

1. Executive Summary

The DEAL CLI ships a local-server, browser-based viewer that renders .dealview-selected model slices as read-only diagrams with fully automatic layout. No human ever adjusts a layout: editing belongs to text today and a commercial GUI later. This document is the codeable rule set that makes that viable — content-driven sizing, guaranteed spacing, connector routing in which no connector ever crosses a SysML element box, crossing-minimizing placement, legibility-driven degradation at scale, and deterministic output persisted back into .dealview tool-managed settings.

Architecture in one sentence: a five-stage worker pipeline (Normalize → Measure → Place → Route → Validate) where ELK Layered places nodes per-container, libavoid routes cross-container edges around every box as an obstacle, d3-flextree lays out pure trees, and a geometric validator proves the invariants before any pixel renders.

2. Problem Statement

Render .dealview-driven diagrams of DEAL model elements as read-only, fully automatic layouts across four phased diagram families: hierarchy/containment, interconnection, traceability, behavior/flow. Rules must cover both nested-container and containment-arrow representations (selected per view in the .dealview), a zoomable canvas whose initial frame is fit-and-centered when readable (else top-left at minimum readable zoom), per-element status badges plus a diagram-level status sidebar, and interactions limited to pan/zoom, select+details, hover trace-highlighting, and expand/collapse. Scale is performance-bounded (1000+ elements possible, no hard cap, graceful degradation). Layout is deterministic per CLI version; resolved settings are written back into the .dealview, which is representation data — never model content — and may be .gitignored (GV-9 preserved: views never affect deal build).

4. Pipeline Architecture

ComponentResponsibility
NormalizeResolve model (.deal/.dealx) + .dealview membership into a ViewGraph IR: nodes, ports, edges, containment, representation mode, status data, persisted settings (if stamp valid).
MeasureCompute node/label dimensions from actual text via cached OffscreenCanvas.measureText with the bundled font (D8). Sizes are facts, never estimates. Cache key: (font-spec, string).

ValidateGeometric checks of all invariants. CI: golden corpus must pass byte-identical. Runtime: violations render with a diagnostics-sidebar warning (S14) — never silently shipped, never a refusal to render.

Viewer shellZoomable SVG canvas, LOD, selection/hover, details panel, diagram-level status sidebar, collapse banner.

5. The Rule Set

Rules carry stable IDs (RG-x.y) so implementation, tests, and future tuning reference them precisely. All dimensions are model-space CSS px at zoom 1.0, integer-valued (RG-1.6). Numbers marked EVIDENCE have research provenance; CONVENTION numbers follow mature-tool practice and are tunable via the spacing profile (RG-8.2) without rule changes.

RG-1 · Sizing & Text

RG-1.1 Node size is content-driven: size = max(minimum, labels + compartments + port footprint + badge reserve + padding). ELK: nodeSize.constraints = [NODE_LABELS, PORTS, MINIMUM_SIZE]. Minimum element box: 80×40. CONVENTION
RG-1.2 All text is measured, never estimated, via OffscreenCanvas.measureText using the bundled woff2 font only (D8), loaded via FontFace in the worker before Measure runs. Results cached per (font-spec, string). Width = TextMetrics.width; height = fontBoundingBoxAscent + Descent.
RG-1.3 Type scale: element name 13px/600; stereotype/keyword («part», «interface») 11px/400; compartment entries 12px/400; port labels 10px/400; edge labels 11px/400. Floor for any rendered text: 10px model-space. CONVENTION (WCAG has no minimum; 24px/18.66px are its only normative cutoffs, used for contrast class only)
RG-1.4 Container/element names soft-wrap at max node width 240px (max 3 lines, then tail ellipsis). Compartment entries and port labels tail-truncate with ellipsis at their column width, minimum 8 visible characters. Full text always available on hover tooltip and in the details panel. Never truncate to fewer than 8 chars — widen the node instead.
RG-1.5 Badge reserve: a 16px-tall strip in the node header (right-aligned) is reserved for status badges at all times, whether or not the status overlay is on → INV-5. Badge glyphs 12px, max 3 + overflow count.
RG-1.6 All final coordinates and sizes round to integers (half-up, deterministic). Strokes 1px (2px selected) aligned to half-pixel grid for crispness; SVG output keeps rendering resolution-independent on any DPI.

RG-2 · Spacing (the channel guarantee)

Spacing is not aesthetic preference — it is what makes D5 provable. With every obstacle inflated by the router buffer (RG-3.4) and the minimums below, an orthogonal route always exists between and around boxes: edgeNode ≥ buffer + 4 and nodeNode ≥ 2·buffer + edgeEdge − 4 guarantee at least one open channel between any two sibling boxes.

RG-3 · Connectors: anchoring & routing

RG-3.1 All edges route orthogonally (ELK edgeRouting: ORTHOGONAL; libavoid routingType: Orthogonal) with 6px rounded corners at bends. Evidence: orthogonal crossings approach 90°, the least harmful crossing angle (Huang et al.); corner rounding aids eye-tracing of turns (Ware et al. 2002 continuity). A per-view curved presentation of the same routed waypoints is available as an opt-in (RG-10.6) — routing computation is always orthogonal/obstacle-avoiding; curved is paint-path geometry only.
RG-3.2 Ports sit on the node boundary. Directed flows: inputs WEST, outputs EAST (left-to-right families) — portConstraints: FIXED_SIDE, order by model declaration (FIXED_ORDER); model-fixed positions use FIXED_POS. Port labels outside the node, 2px gap.
RG-3.3 Non-port relations anchor at a layout-chosen point on the box boundary — never at corners (min 8px from any corner), minimum 12px separation between anchors on the same side, and the first segment departs perpendicular to the side for ≥ 12px before any bend.
RG-3.4 The no-cross guarantee (D5/INV-1). Intra-container edges: ELK Layered routes in inter-layer channels — node-avoiding by construction. Cross-container edges: libavoid with every element box and label box (S13) registered as an obstacle; shapeBufferDistance: 12, idealNudgingDistance: 8, ports as fixed ShapeConnectionPins with directions. ELK's INCLUDE_CHILDREN mode is prohibited (known broken cross-hierarchy routing: eclipse-elk #700, #776).
RG-3.5 Container walls (S12). An edge may cross a container boundary only if it connects to that container's interior, exactly once per wall, perpendicular at the crossing point. Containers not on the edge's containment path are hard obstacles.
RG-3.6 Edge–edge crossings are minimized (ELK crossingMinimization: LAYER_SWEEP + greedySwitch), and when unavoidable occur at 90° only (INV-6). Branch points render as plain T-junctions — no dot (the filled circle is reserved as proxy-label notation); crossings are disambiguated by hops (RG-10.8), so an unhopped meeting unambiguously reads as a branch. No optimality promise — crossing number is NP-hard; layer-sweep barycenter is the accepted quality/cost point.
RG-3.7 Edge labels render with an opaque background halo (2px), centered inline on the edge; multiplicities/roles at ends with 4px offset. Label boxes are routing obstacles (S13): where conflict is unavoidable, the label wins and the edge nudges.
RG-3.8 Self-loops route on the node's EAST side with 16px clearance (spacing.nodeSelfLoop). Edge merging/bundling is OFF except the sanctioned same-source/same-kind merge of RG-10.9 — general bundling measurably harms individual-edge traceability; the RG-10.9 merge is identity-preserving (same relationship semantics, per-branch refs) and is the only exception.
RG-3.9 Arrowheads 10px long; router buffer (12) ≥ arrowhead so heads never overlap boxes they don't target.
RG-3.10 Bend minimization & port alignment (auto-mode). After crossing minimization (the dominant comprehension factor, RG-3.6), the layout minimizes bends — the second-ranked aesthetic in the evidence (Purchase et al.): zero-bend straight connections are the target. To achieve them, Place aligns connected port pairs on a shared axis whenever feasible (ELK: nodePlacement.strategy: NETWORK_SIMPLEX already favors edge straightness; port positions chosen so facing ports line up center-to-center), and multiple ports on a shared face are equal-spaced, ordered to match the vertical/horizontal order of what they connect to (RG-3.2 FIXED_ORDER from model order, adjusted by the RG-4.3 affinity pre-pass). Bends appear only when alignment is geometrically impossible, and then per RG-3.1/RG-10.7 discipline.

RG-4 · Placement

RG-4.1 Flow direction per family: hierarchy top-down; interconnection left-to-right (elk.direction: RIGHT); behavior/flow top-down (DOWN, feedbackEdges: true); traceability left-to-right by relation direction.
RG-4.2 All heuristic ties break by model declaration order: considerModelOrder.strategy: NODES_AND_EDGES. This yields determinism and gives authors layout influence through the text — reorder declarations, reorder the diagram.
RG-4.3 Cross-edge affinity pre-pass (S8). Before placement, sibling containers are ordered by descending cross-edge density (connected pairs adjacent where possible). Mitigates SEPARATE_CHILDREN blindness to cross-container edges. v1 optimizes correctness; route-length aesthetics iterate behind this stable schema.
RG-4.4 Layered defaults: nodePlacement.strategy: NETWORK_SIMPLEX, layering.strategy: NETWORK_SIMPLEX, cycleBreaking: GREEDY, unnecessaryBendpoints: true, thoroughness: 10.
RG-4.5 Nested mode: children laid out per-container bottom-up; container size = children bounding box + RG-2.5 padding. Containment-arrow mode: d3-flextree (variable node sizes, RG-2 gaps), parent above children, orthogonal elbow links — crossing-free by tree property.
RG-4.6 Disconnected components pack row-wise left-to-right, top-down, in declaration order, RG-2.7 gaps.

RG-5 · Viewport & zoom

RG-5.1 Initial frame: compute fitZoom (diagram fits viewport − 24px margin, centered). If fitZoom ≤ 1.0 AND element-name labels render ≥ 11 effective px at it → open fit-and-centered. Else → open at readableZoom = 11 / 13 ≈ 0.85 anchored at the diagram's top-left with 24px margin. Never open above 100%.
RG-5.2 Zoom clamp [0.05, 4.0]; wheel/pinch zoom centers on cursor; pan unbounded within diagram bounds + ½ viewport.
RG-5.3 Rendering is SVG (vector): crisp at any devicePixelRatio by construction; no raster fallback in v1.

RG-6 · Scale & legibility-driven degradation

RG-6.1 Legibility budget: 50 visible first-class elements EVIDENCE (7PMG, Mendling et al. 2010 — error rates climb above ~50 elements). Above budget, deepest containers auto-collapse first until within budget or nothing remains collapsible. A collapse banner reports "N containers collapsed for legibility" with one-click expand (S16). Per-view budget override persisted via RG-8.2.
RG-6.2 LOD bands (projected zoom): < 0.3 → titled boxes only (no ports/compartments/edge labels); 0.3–0.6 → + edges and port shapes, no port labels, compartments summarized as counts; ≥ 0.6 → full detail. Any label whose projected size < 8px is not rendered. CONVENTION (KLighD smart-zoom pattern; Cytoscape minZoomedFontSize practice)
RG-6.3 LOD stability invariant: anything visible at detail level n remains visible at n+1 (GraphMaps principle). Zooming in only ever adds.
RG-6.4 Performance valves: layout always in a Web Worker; > 300 visible nodes → progressive render with progress UI; > 1500 visible nodes → require collapse (banner + CLI warning). elkjs measured reality: ~1–5s at 1k nodes with ports.

RG-7 · Interaction & stability

RG-7.1 Expand/collapse relayouts the affected container and its ancestor chain only (a SEPARATE_CHILDREN property); sibling order always preserved (RG-4.2). The toggled element is viewport-anchored — it stays put on screen, the world moves around it (S15). Transition 200ms ease-out.
RG-7.2 Hover highlights the element + its edges + direct neighbors; everything else dims to 30% opacity. No layout change.
RG-7.3 Select applies a 2px accent outline + opens the details panel (properties, full untruncated text, element diagnostics). No layout change.
RG-7.4 Status overlay toggle changes paint only (badges, border/fill accents) — zero position deltas (INV-5, enabled by RG-1.5). Diagram-level status lives in the sidebar, not on the canvas.
RG-7.5 Go-to-definition. Every rendered element — boxes and compartment entries, which are elements themselves — carries its stable qualified name as data-ref (identity, never file/line: source spans go stale, identity doesn't). Cmd/Ctrl+click or double-click on a ref carrier emits navigate(ref); plain click remains selection (RG-7.3). The shell resolves ref → source span at click time via the model index (the LSP already owns this mapping) and opens the user's editor (e.g. vscode://file/...:line:col URI or a local-server $EDITOR endpoint). Hover affordance: underline on ref carriers, paint only. The shell uses one delegated listener on the canvas, not per-element wiring — O(1) listeners at any diagram size. Navigation never alters layout. Reference implementation: DEAL-Viewer-Component-ElementBox.html.

RG-8 · Determinism & persistence

RG-8.1 Same (model content, view definition, CLI version) → byte-identical SVG on any machine. Requires: bundled font measurement (D8/RG-1.2), no unseeded randomness (any stochastic option gets randomSeed: 1; the chosen algorithms are deterministic), integer rounding (RG-1.6), model-order tie-breaking (RG-4.2).
RG-8.2 Write-back. The Settings Writer maintains a tool-managed block in the .dealview containing: organizational-structure choice, representation mode (if auto-chosen), resolved spacing profile, collapse states, container-order hints, legibility-budget override — stamped with engineVersion + inputHash (model + view membership content hash). Valid stamp → settings reused (stability + render cache). Stale stamp → full relayout, block rewritten. Human-authored membership is never touched by the writer.
RG-8.3 .dealview files are representation artifacts, categorically distinct from .deal/.dealx: gitignore-able, never required for deal build (GV-9), never element-declaring (GV-13).

RG-9 · SysML v2 Graphical Notation

Element rendering follows the SysML v2 graphical notation (reference: owner-provided decomposition-view example, 2026-06-11). These rules bind RG-1 sizing to concrete box anatomy.

RG-9.1 Diagram frame. Every rendered view sits in a rectangular frame with a name tab (slant-edged, per RG-9.10) at top-left containing the view kind and subject, e.g. Decomposition View of vehicle. The frame is the pannable canvas boundary (INV-7). When the view subject is a package, the frame renders as that package's folder (RG-9.10).
RG-9.2 Element box anatomy (top to bottom): rectangle, 1.5px stroke, with corner style by element class — definition elements («part def», «requirement def», «allocation def», …) have square corners (0 radius); usage elements («part», «requirement», …) have rounded corners (8px). Classification is automatic (keyword ends in def → definition), overridable per element. Header = centered «keyword» line (11px) above centered bold qualified name (13px/700), name may carry a multiplicity suffix (e.g. cylinders[6]); a rule at the box stroke weight (1.5px) closes the header only when compartment content follows — header-only elements are closed by the outer box alone (RG-9.7); then zero or more compartments (the count is open — 1, 5, or none), each opened by a centered italic category label (10.5px — attributes, ports, perform actions, exhibit states, …) with left-aligned 12px entries, one per line, 1px rules between compartments. Compartment presence is content-driven (RG-1.1); empty compartments never render. Reference implementation: DEAL-Viewer-Component-ElementBox.html.
RG-9.3 Entry decorations render verbatim from the model: visibility prefix (+ public, − private, # protected) and multiplicity suffix ([0..1], [1..*], …). Decorations participate in text measurement (RG-1.2) — never truncated away while the entry name survives.
RG-9.4 Containment connector (containment-arrow mode, D4). Solid orthogonal line with a filled black diamond at the parent end (composition), one diamond per relationship, anchored on the parent's child-facing side (bottom for top-down trees, RG-4.1) per RG-3.3 anchor rules. Parent renders above children; tree edges are crossing-free by construction (RG-4.5). The diamond glyph (12×8px) counts as part of the edge for INV-1 — it touches, never overlaps, the parent boundary.
RG-9.5 Badge placement vs anatomy. The RG-1.5 badge reserve occupies the right end of the header's keyword line (top-right corner inside the box), so badges never collide with the centered name and toggling stays layout-neutral (INV-5).
RG-9.6 Brand theme — paint only, never geometry. Two themes ship: standard notation (pure black, conformance/export mode) and the DEAL brand theme. Both produce pixel-identical geometry; a theme is exclusively CSS custom properties (--eb-*) keyed off the element's data-family/data-kind. Brand theme: family-tinted header band (light fill behind the header, following the box's corner radius), outline + header rule + «keyword» in the family accent, compartment separators in quiet gray inset 12px from each edge (inset applies in all themes — geometry constant). Family palette (light / dark variants): part steel-blue, requirement green, action violet, state teal, interface/port amber, constraint maroon, allocation slate, package manila (folders read as folders), fallback gray. Names render near-black/near-white at ≥4.5:1 contrast — color encodes family only, never information; the diagram must survive grayscale. Reference implementation + palette: DEAL-Viewer-Component-ElementBox.html.
RG-9.7 Fold affordance. Governing principle: if the header alone carries the information, the outer box closes it — no header rule, no footer. The moment an element has any compartment content, it gets both the header rule and a fold footer: a full-width 16px strip at the box bottom containing a centered chevron (up = fold, down = expand); the entire strip is the click target. Expanded, the strip is separated from the last compartment by a 1px rule; collapsed (header + footer only), the strip sits directly under the header rule, which doubles as its separator — never two stacked lines. The footer is present in both fold states, so toggling changes only the compartment region; in the brand theme it tints like the header band. Folding triggers the RG-7.1 relayout contract (ancestor chain only, viewport-anchored, sibling order preserved); per-element fold states persist via RG-8.2.
RG-9.8 Badge slots. Header badges occupy three named slots in the keyword line, right-aligned inside the box padding, fixed order left→right: semantic (innermost), diagnostics, verification (outermost — verification status reads first at the box corner). Content contracts: semantic = one of {abstract A, variation V, redefinition R}, always dim tone; diagnostics = computed glyph, worst severity wins (✖ errors over ⚠ warnings) with count, capped at 9+; verification = exactly one of {✓ pass (good), ✗ fail (bad), ○ unverified (dim)}. Tones come only from the semantic palette (good/warn/bad/dim) — never free-form color. Slot widths are measured per glyph (RG-1.2) and the keyword stays centered against the symmetric reserve (RG-9.5); empty slots collapse. Every badge carries a tooltip naming its meaning. Unknown slots or out-of-registry values are rejected by validation and never drawn — they surface as Validate-stage diagnostics (S14), not as best-effort rendering. Occupancy derives from model/status data, never from the overlay toggle, preserving INV-5.
RG-9.9 Port notation. Ports render as rounded squares straddling their owner's boundary (18×18 base, 4px radius, 1.5px stroke; elongated for container-scale ports), with an opaque canvas fill — the boundary line never shows through. An optional flow-direction glyph renders inside: in / out / inout arrowheads on a short line whose axis rotates with the hosted edge — horizontal on E/W edges, vertical on N/S edges — always running along the connector tail, with in pointing from outside the boundary to inside and out from inside to outside. Labels (name: PortDef, 11px, horizontal) render inside the port box when it is large enough to host them (measured per RG-1.2, never guessed); otherwise they float outside, above and near the connector, on the connector side of the boundary — never over the owner. Tall ports may rotate their internal name — the only sanctioned rotated text in the notation. Ports nest: a port's own boundary hosts child ports (the Place stage positions them; nesting depth is unbounded). Connectors attach to a port's outer face under the RG-10.7 approach discipline — and port-to-port connect edges carry no arrowheads: the port is the termination of the line, with flow direction expressed by the port glyphs, not the edge, and every port carries its element data-ref (RG-7.5). Reference implementation: renderPort() in DEAL-Viewer-Component-Connector.html.
RG-9.10 Package (namespace) notation. Packages — namespaces used solely to organize the model (OMG SysML v2 §7.5) — render as folders: a slant-edged tab (24px, top-left; owner-drawn reference 2026-06-12) over a square-cornered body. The package is the outermost containment: when a view's subject is a package, the folder is the diagram frame (RG-9.1 and RG-9.10 are the same construct). Name placement: in the body (centered bold, empty tab) or in the tab (left-aligned, bold 14px) — both valid; packages showing members carry the name in the tab. Semantics the notation must respect (§7.5): members relate via Membership, which carries a member name and a visibility («private» = not visible outside); an element has at most one owning membership across all namespaces (duplicate owned renderings → Validate diagnostic, S14); non-owning membership may introduce an «alias» (folder variant with bold-for target line); imports create unowned memberships — imported packages render dashed (nested notation), and the star notation is verbatim: no star = element, * = package contents, ** = recursive including owned sub-namespaces; package filter conditions are resolved by Normalize — rendered member lists always show resolved members, never filter expressions. All definitions and usages are themselves namespaces — member-list anatomy, nesting, and ports all inherit from this rule. Qualified names (A::B::c) are notation only; the abstract syntax holds actual references — which grounds RG-7.5: data-ref is identity, resolved by the model index, never parsed. Member entries render their leading keyword bold with per-entry refs; optional italic compartment title; brand theme tints the tab manila. Membership (⊕ owned / ○ alias) and dashed-arrow «import» connectors are deferred to the relational companion document. Reference implementation: DEAL-Viewer-Component-Package.html (own component contract, peer to ElementBox and Connector).

RG-10.1 Closed registry. Connector kinds, glyph geometry, glyph end, and declaring-file type live in one registry shared by renderer, validator, and documentation. Unknown kinds render as a plain line plus a Validate-stage diagnostic (S14) — never a guessed glyph.
RG-10.2 Geometry & crispness. Glyphs are drawn in model space, axis-aligned to the final orthogonal segment, sized relative to the universal 1.5px stroke (triangle 12×12, diamond 14×10, dots r1.6, single bar 8px). Hollow interiors fill with the canvas background so crossings read correctly. Everything scales proportionally with zoom (pure vector — no non-scaling-stroke), so connectors read identically at every zoom level; below the 0.3 LOD band labels drop but glyphs persist (RG-6.2).
RG-10.3 Line shortening. The line never pokes through a hollow glyph: the glyph-end segment is shortened by the glyph's total length (head + adornment), and the glyph tip touches the anchor point on the element boundary (RG-3.3/RG-9.4).
RG-10.4 Traceability. Every connector carries the stable identity of its relationship declaration as data-ref (compositions/memberships declare in .dealx; subclassification/redefinition in .deal) plus data-kind. Navigation follows the RG-7.5 contract: Cmd/Ctrl+click or double-click → navigate(ref), resolved to a source span by the shell at click time. A 12px invisible hit path makes connectors clickable without pixel hunting.
RG-10.5 Neutral color. Connector stroke is neutral in every theme — relationship meaning is carried by glyph shape alone, never color (grayscale-safe, color-blind-safe). Color on connectors remains reserved for status overlays (e.g., highlighting a failing trace) per RG-7.2/RG-7.4.
RG-10.6 Routing style: orthogonal | curved. A per-view representation setting (one style for the whole view — never mixed per connector — persisted in the .dealview tool-managed block, RG-8.2). Orthogonal (default): rounded 6px bends per RG-3.1. Curved: a smooth cubic chain through the same obstacle-avoiding waypoints the Route stage produced, with handle lengths clamped so the curve's deviation from the polyline stays below the 12px routing buffer (RG-3.4) — therefore INV-1 holds in both styles by construction, since the polyline itself keeps ≥ buffer distance from every box. Endpoint tangents align with the first/last segments so glyphs (RG-10.1) anchor and orient identically in both styles. Unknown style values render orthogonal + a Validate diagnostic (S14). The placement/routing pipeline is unchanged — routing style is paint-path geometry only, downstream of Route.
RG-10.7 Approach discipline. At both ends of every connector: (a) the final segment is perpendicular to the anchored element face — axis-aligned, entering opposite the face's outward normal, never at a corner (≥8px clearance, RG-3.3); (b) the line stays straight for the glyph's full length + 12px run-out beyond the anchor before its first bend — bends crowding an arrowhead read as glitchy and are prohibited. Applies in both routing styles: curved mode pins the run-out zone straight with synthetic waypoints, so curves bend no earlier than orthogonal routes do. The Route stage produces conforming geometry (anchor + first-bend placement); the connector component validates every connector against (a) and (b) and emits Validate-stage diagnostics (S14) for violations — flagged rendering, never silent acceptance, never component-side "fixing" that would mask a Route bug.
RG-10.8 Crossing treatment. Edge–edge crossings occur only at 90° (INV-6 — guaranteed in orthogonal routing: every crossing is one horizontal × one vertical segment). At every crossing, the horizontal segment carries a Visio-style hop: a 4px semicircular bump bulging upward — a deterministic convention giving exactly one hop per crossing, never both lines. Hops closer than 10px (2r + 2) on the same segment merge into one wider hop. Crossings at endpoints/junctions are excluded — those are branches, which render as plain T-junctions (RG-3.6); the hop itself is the disambiguator (hopped = crossing, unhopped meeting = branch). Collinear overlapping segments are prohibited — Route must hold ≥12px edge–edge spacing (RG-2.4); overlaps surface as Validate diagnostics (S14). Hops are an orthogonal-mode feature: curved mode renders crossings plain (angles not guaranteed) — a documented trade-off of choosing curved (RG-10.6).
RG-10.9 Same-source bundling. Connectors of the same kind originating from the same source element auto-merge: a single shared trunk runs from the source while the members' corridors stay within 24px proximity, splitting as a plain T-junction — no dot (RG-3.6; the filled circle is reserved as proxy-label notation) — single tail until the split, then branches to each target. Glyph placement follows the shared end: when the glyph end is the shared end (composite/member diamonds at the owner), the bundle carries one shared glyph on the trunk; target-end glyphs (triangles) render per branch. Identity survives merging: every branch carries its own relationship data-ref (trunk hover highlights the bundle; branch hover and navigation address the individual relationship). Route produces bundle members with a shared waypoint prefix; the mirrored shared-target merge (the classic generalization tree) is the same algorithm suffix-wise and is Route's call. This is the only sanctioned merging — see RG-3.8.
RG-10.10 Association connector & inline keyword label. The association arrow (filled barbed head, 14×11 with 4px concave rear — the line runs into the notch) serves multiple relationship uses, qualified by an optional «keyword» label rendered verbatim («satisfy», «import», «type», …) or unlabeled for bare action succession (then). The label is always horizontal — never rotated — and sets into a break in the tail at 11px (RG-1.3). Formatting follows content: «keyword» labels (stereotype-qualified associations) render italic in guillemets; element names — the via cable/interface on a connection, e.g. HVDCCable — render plain upright, no guillemets: names are model elements, not stereotypes. On horizontal hosts the line gap is the label width + 12px; on vertical hosts the label sits perpendicular to the line, straddling it, with a gap of the text height + 12px (label–box clearance is Route/INV-3's concern). Initial placement rule: centered on the longest hosting segment (horizontal preferred on ties), outside the RG-10.7 run-out zones. In curved mode, or when no segment can host the gap: RG-3.7 halo label beside the path — still horizontal at any line tangent, no break. Labels drop below the 0.3 LOD band like all edge labels (RG-6.2).
RG-10.11 Label slide — the only user-adjustable geometry. The user may drag an inline connector label along its line — across horizontal and vertical portions alike, the label staying horizontal throughout; the drag projects onto hosting segments and the committed position persists as labelAt (normalized 0..1 path distance) in the .dealview tool-managed block (RG-8.2). This is a sanctioned, narrow exception to D1: a representation-state adjustment (like fold states and routing style), never layout editing — it cannot move elements or alter routing, and it resets when a relayout invalidates the settings stamp. Hit-target deconfliction: the label owns an exclusive padded hit box (label bounds + 6px, grab cursor, hover highlight); the line's 12px hit corridor is built from the gap-cut polylines, so it never overlaps the label zone — and line hover affordances trigger only from the line's own corridor, never the label's. Decision logged as D11.
RG-10.12 Connection explainer card. Dwelling on a connector (hover ≥500ms — casual mouse travel never flashes cards) raises a pop-up card explaining what the connection denotes, in four parts: (1) a plain-language reading composed deterministically from registry-owned sentence templates and the endpoints' display metadata (name + classifier, supplied by Normalize) — e.g. "The SteeringWheel part satisfies the SteeringMechanism requirement." — with association readings derived from the «keyword» (satisfy→satisfies, import→imports, …; unlabeled = succession); (2) the kind's general meaning; (3) the glyph-direction note (which end the symbol sits at and why); (4) the declaration ref, its declaring file type, and the navigate hint. Content is never free text — templates live in the connector registry beside the glyph definitions, so reading, rendering, and validation cannot drift apart. The card is a paint-only overlay (placed beside the cursor, flipping to stay on-screen), dismissed on leave; no cards below the 0.3 LOD band (RG-6.2). Reference implementation: connectorExplanation() in DEAL-Viewer-Component-Connector.html.
RG-10.13 Minimum connector length. A connector's routed path must be long enough that its parts fit: minLen = glyph length + 2 × 12px run-outs + (inline label gap, when labeled) — derived per connector from its kind and label, never a fixed constant. Any shorter and the rendering degrades to "nothing but the text between the ends." The Place stage guarantees this by construction (RG-2 spacings already keep facing boxes ≥ 32px apart; labeled connectors may require Route to lengthen a path or Place to widen a gap); the component validates every connector and emits an RG-10.13 diagnostic (S14) when violated. Port-to-port connect edges have zero glyph length, so their minimum is run-outs + label gap.

7. Invariants (CI-tested geometry)

Invariants are the contract. The Validate stage checks them on every layout; CI checks them (plus byte-identity) over a golden corpus of example models that doubles as the example library. Runtime violation → render + highlight in diagnostics sidebar + deal view doctor report (S14). A violation is always a bug, never a configuration.

INV-1 No-cross (D5). No edge segment intersects any element box or label box, with the RG-3.5 container-wall exception: an edge crosses a container boundary only if it connects to that container's interior, exactly once per wall, perpendicular at the crossing.
INV-2 No two element boxes overlap; all RG-2 minimum spacings hold.
INV-3 No label–label overlap; every label is unambiguously associated with exactly one element/edge (nearest-feature distance ratio ≥ 2:1).
INV-4 Re-rendering the same (model, view, CLI version) yields byte-identical SVG.
INV-5 Toggling the status overlay produces zero position deltas.
INV-6 Edge–edge crossings occur at 90° only and carry a hop on the horizontal segment (RG-10.8); branch points are plain T-junctions with no hop and no dot (RG-3.6).
INV-7 The initial frame satisfies RG-5.1; no element lies outside the pannable canvas.
