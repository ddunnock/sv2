The third atomic component: the namespace container everything else lives in. Framework-free JS producing SVG, folder silhouette with the slant-edged tab (owner-drawn reference), content-driven sizing, both themes, refs and navigation per RG-7.5. The <script> below lifts into the viewer codebase as package.js.

1. Namespace semantics (OMG SysML v2 §7.5) — what the component must respect

SemanticConsequence for rendering
A namespace contains elements and provides names for them; members relate via Membership, which can carry a member name and a visibility (visible outside the namespace or not).Member entries may carry visibility decorations; «private» marks members/imports hidden outside the namespace.
Owned membership: deleting the namespace deletes owned members. An element has at most one owning membership across all namespaces, but may additionally hold non-owning memberships — including in the same namespace.Owned members render solid; the ⊕ membership connector marks the owning end. One owner ever — duplicate solid renderings of one element in two packages would be a model error (Validate diagnostic).
Non-owning membership may introduce an alias name relative to the namespace.«alias» folder variant with the bold-for target line; ○ connector glyph for unowned membership.
Import brings memberships in from another namespace — imported members become unowned members of the importer. Star notation: no star = single element, * = package contents, ** = recursive including owned sub-namespaces.Imported packages render dashed (nested notation); the «import» dashed-arrow connector carries the star suffix verbatim.
A package is a namespace used solely to organize the model, and may filter imported elements by metadata conditions — recursive import + filtering = automatic content selection across the model.Filter conditions are model semantics (Normalize resolves actual membership); the rendered member list always shows the resolved members, never the filter expression as members.
All definitions and usages are also namespaces. Namespace rules apply generically.This is why ports nest, parts own parts, and the member-list anatomy is shared — the package is just the purest container case.
Qualified names (A::B::c) are notation only — the abstract syntax holds actual element references, resolved by name resolution.Grounds RG-7.5 exactly: data-ref carries identity; the shell/model index resolves it at click time. Display strings use qualified names; navigation never parses them.

4. Component contract

renderPackage(spec, opts?) → { node: SVGGElement, layout: {width, height} }

spec = {
  name,
  namePlacement?: 'body' | 'tab',  // default: 'body' when simple, 'tab' when members shown (OMG: both valid)
  keyword?,                        // «alias», «private», … — keyword line above a body-placed name
  forTarget?,                      // alias target → bold "for Package2" line (non-owning membership)
  dashed?,                         // imported package, nested notation (unowned membership via import)
  compartments?: [{ title?,        // title OPTIONAL — owned members may list directly
                    items: (string | {kw?, text, ref?})[] }],  // kw renders bold: "part def" PartDef1;
                                   // visibility (+/−) and star suffixes (* / **) render verbatim (RG-9.3)
  minWidth?, minHeight?,           // frame-scale sizing for outermost containment (pass opts.maxWidth too)
  ref?                             // qualified name as display identity — navigation per RG-7.5
}
opts = { maxWidth?, onNavigate?: (ref) => void, theme via CSS vars --eb-* }
